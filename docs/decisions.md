# Decision Log

Durable architectural and product decisions a future contributor needs to know, so they aren't accidentally reversed. Not a full history — see the historical documents indexed in `README.md` for the exhaustive record. Each entry: **Decision / Why / Consequences**.

---

### Locked hierarchy: Project → Service → Activity → Task → Checklist

**Decision**: This is the final, accepted product hierarchy. No Subtask level exists.
**Why**: A Subtask concept (`tasks.parent_task_id`) was built, then deliberately removed — the Product Owner's final call, recorded verbatim in the removal migration: *"THERE ARE NO SUBTASKS IN COREBRIDGE X."*
**Consequences**: Unexpected additional work becomes another ordinary Task, never a nested item. Do not reintroduce task nesting. See `domain-model.md`.

---

### "Service" is the only visible term; "Workstream" stays internal — **superseded by Phase 1, see below**

**Decision**: Every user-facing surface says "Service." "Workstream" is confined to code (types, table names, routes, RPC/RLS names).
**Why**: Product terminology was locked to match how the business actually talks about client work, without forcing a full schema rename.
**Consequences**: New UI copy must never say "Workstream." New code may freely use `Workstream`/`workstream*` identifiers — that's expected and correct.

**Superseded 2026-09-22 (CD-206, Phase 1 Template workspace)**: the visible term is now "Template," not "Service" — see the "Phase 1 — Template workspace and terminology" entry further down for the full decision. The pattern this entry established (internal code/table/route names never have to match the visible product word) is exactly what Phase 1 reused — only the visible word itself changed a second time.

### Global staffing never implies Project-level authority

**Decision**: "Global Team Lead" (Services Led) and "Works In Services" are org-wide, per-catalog-Service-Line relationships. They never automatically grant leadership or team membership on any specific Project's Service instance.
**Why**: Explicit product decision, stated directly in code: *"a global Team Lead relationship grants no automatic Project authority in V1."*
**Consequences**: Adding someone to a Project's Service (as lead or team member) is always a separate, explicit action — never inferred from their global staffing record. See `domain-model.md`'s comparison table.

### Comments is the one canonical discussion mechanism; Notes and Handoff authoring are retired

**Decision**: New Task/Project discussion happens in Comments. Creating a new "Task Note" or a new "Task Handoff" is retired — no UI exists to author either.
**Why**: Consolidation of what had become three overlapping discussion mechanisms into one.
**Consequences**: Historical Notes/Handoff data is preserved read-only, not deleted. Ownership transfer today is "change Assignee(s) + add a Comment," not a Handoff record. Company-level Notes ("Client Context") is a separate, still-live feature — don't confuse the two.

### Team Activity is a UI/navigation merge, not a data-model merge

**Decision**: `/dashboard/team-activity` replaced two separate pages (Team Updates, Team Time), sharing one roster/date/selection shell. `daily_updates` and `time_entries` remain two entirely separate tables/models.
**Why**: The two old pages shared ~70% identical chrome (roster card, date stepper, empty states) despite representing genuinely different business concepts — merging the shell removed real duplication without forcing an unnatural data-model merge.
**Consequences**: Don't look for a unified "team activity" table — there isn't one. Old bookmarks to the two retired routes still work via a 307 redirect (temporary, not cached hard) to the correct tab of the new page.

### Local calendar-date semantics, not UTC slicing, for "which day does this belong to"

**Decision**: Any code answering "what calendar day is this for the user" must use `src/lib/planner-dates.ts`'s helpers (`dateKeyFromTimestamp`, `localDayBoundsUtc`, `todayDateOnly`, `parseDateOnly`) — never a raw `.toISOString().slice(0, 10)`.
**Why**: A real defect (found during CD-190 stabilization): a manually-logged "Duration" mode time entry, anchored at local midnight, was misclassified onto the *previous* calendar day for any positive-UTC-offset user, because the reading code took a naive UTC-string-slice instead of converting back to local time. See `troubleshooting.md` for the full mechanism.
**Consequences**: The fix was applied narrowly (mock/Supabase time-entry date-scoped queries, My Day's Today card, the manual time-entry dialog's date handling) — it was **not** applied to the many other UTC-slice call sites across the app (due-date/overdue classification, various default-date fields) that share the same anti-pattern but weren't in scope for that fix. Tracked as its own follow-up ticket (CD-193, `Corebridge X — Normalize local-date handling across task and dashboard date surfaces`) — see `current-state.md`. Don't assume every UTC-slice call site has been fixed; check each one.

### Project vs. Company: Project is the visible client workspace; Company is the technical record underneath

**Decision**: `/dashboard/projects` is the one primary destination for every role. `/dashboard/companies` still exists and still holds the real underlying data/RLS, but is no longer a primary nav item and is reachable mainly by direct URL for Admin-level technical administration.
**Why**: Simplification pass — most day-to-day editing (brand, status, contacts) now happens inline on a Project's own Overview tab via the same dialogs Company detail uses, so visiting Company detail directly became rare.
**Consequences**: Company as a concept/table/RLS boundary is not deprecated — don't remove it. It's demoted in navigation prominence, not in architecture.

### Read-broad, write-narrow authorization split (Documents, and a reusable pattern elsewhere)

**Decision**: For Task-linked Documents, viewing/downloading uses the broad `canAccessTask` check; uploading, editing metadata, soft-deleting, and restoring use the narrower `canAccessTaskDirectly`.
**Why**: Viewing is safe to extend to anyone with legitimate visibility into a Task's hierarchy; mutating is a stricter boundary.
**Consequences**: This pattern (broad read / narrow write) recurs elsewhere in the authorization model — recognize it rather than treating each occurrence as a one-off when reviewing new permission functions.

---

### Deactivating a user must revoke role-based privileges everywhere, not just at the DB layer

**Decision**: Every core role-check function (`isSuperadmin`, `isSupervisor`, `isEmployee`, `managesUser`) folds in an `active` check.
**Why**: A defense-in-depth gap was found where several RLS policies/RPCs gated access via a raw `<column> = auth.uid()` ownership check that never called a role-helper function at all — meaning a deactivated user's existing ownership could still pass. Fixed via a canonical `is_current_user_active()` SQL helper composed into every authorization entry point.
**Consequences**: When adding a new permission check (app-layer or RLS), compose the existing active-user helpers rather than writing a fresh ownership check from scratch.

### Dashboard vs. My Day: role-scoped overview vs. personal execution

**Decision**: `/dashboard` and `/dashboard/my-day` answer two different questions and are no longer allowed to drift toward each other. **Dashboard** = "What is happening across my scope, and what needs attention?" — summary, health, oversight, attention, navigation into operational surfaces; it must never become a second Tasks editor. **My Day** = "What am I personally doing now and next?" — personal execution, personal Tasks, personal Time/Timer, personal Upcoming, personal Daily Update, Today/Week/Month planning; it is **personal by default for every role**, with exactly one deliberate planning exception (below).

Concrete placement decisions:
- **Notifications** → Dashboard only, for every role (Employee/Team Lead/Admin all show `RecentNotificationsCard` on their Dashboard now; it is removed from all three My Day variants). Notifications is an awareness/context signal ("what happened that I should know about"), not personal execution.
- **Employee's personal Upcoming** → My Day Today only (removed from Employee Dashboard, which has no Upcoming card at all now).
- **Team/Organization Upcoming** → stays on the Team Lead/Admin Dashboard, explicitly labeled "Team Upcoming" / "Organization Upcoming" (never bare "Upcoming") so it's never confused with a viewer's own personal Upcoming on My Day. This is a genuinely different scope from Client Health or Recurring Work Due, not a duplicate of either — kept, not removed.
- **Needs Attention** (`NeedsAttentionStrip`) → moved from Team Lead's/Admin's My Day to their Dashboard (Employee never had this — Dashboard oversight strips are a management-only concept, not added to Employee's Dashboard).
- **Today vs. Week/Month** → My Day's Today-only cards (Today Time, personal Upcoming, Daily Update) now render only under the Today tab; Week/Month show just the tab bar, filter bar, and calendar grid. Previously all three rendered unconditionally regardless of which tab was selected.
- **Team Lead's Week/Month "My work | Team" toggle** → kept (not retired), defaulting to "My work". Team Activity is a Daily Update/Time review surface, not a Week/Month scheduling surface, so it cannot replace this toggle.
- **Admin's Week/Month schedule default** → fixed to default to the Admin's own assigned tasks (via `useTaskFilters`'s new optional `initialFilters` parameter — a per-page override, not a change to the global `DEFAULT_TASK_FILTERS`), matching every other role's My Day. The existing Assignee filter still lets an Admin explicitly widen to another person or "All assignees."
- **Activity feed naming** → "Recent Team Activity" / "Recent Firm Activity" both renamed to "Recent Task Activity" on Team Lead's and Admin's Dashboard (visible label only — `TeamActivityCard`'s underlying data/model is unchanged, and the real `/dashboard/team-activity` page/nav item keeps its own name).
- **Dashboard vs. My Day header** → Dashboard's `<h1>` is now the literal word "Dashboard" plus a role-and-scope-aware subtitle; My Day keeps the personal greeting (`GreetingText`) it always had. Previously both surfaces rendered byte-identical greeting markup, which was the single biggest reason the two pages read as duplicates.
- **Dashboard KPI drill-down is navigation/read-only, not a parallel Task editor** → the popover a Dashboard KPI tile (My Open Tasks, Overdue, Completed This Week, Team Open Tasks, Active Tasks, etc.) expands into (`TaskKpiDetail`) no longer wires an `onEdit`/`onDeleted` kebab menu onto its task rows — a row click still opens the same real Task Drawer used everywhere else in the app, but there is no in-popover Edit/Delete. This is scoped to exactly the KPI-tile popovers; it does **not** touch the "Tasks by Status" donut's own expand dialog (`TaskStatusFocusContent`, a different component), which still offers its existing kebab — that surface wasn't part of the KPI-drill-down correction and was left as a known, separately-trackable question if the Product Owner later wants Dashboard fully read-only everywhere. `TaskKpiDetail`/`TaskSummaryItem`/`TaskActionsMenu`/`TaskDrawer` themselves were not modified or removed — only the three Dashboard files' own wiring changed, since those components are shared with Planner/Tasks and remain fully editable there.
- **A notification must know the viewer before it can safely resolve a destination** → `notificationHref(notification, viewer)` (`src/lib/data/notification-links.ts`) takes the current user and returns `string | null`, never a guessed/invalid URL. Root cause it fixes: a `report-comment` notification (a comment on a legacy internal Accomplishments Report) always linked to `/dashboard/reports/[id]`, but that page was separately gated Superadmin-only for direct navigation — so the report's own Team Lead/Employee owner, exactly who that notification is for, hit a dead-end "Internal Reports have moved" page instead of their own report. The fix resolves that destination only for a Superadmin viewer; for anyone else (or when any type's own required id is missing/`null`) it returns `null`, and both consumers (`RecentNotificationsCard`, `NotificationsBell`) render a `null` href as plain, non-interactive, still-readable content — never a link that can dead-end or 404.
- **Dashboard Notifications visual language borrows from Project Services, not from its own bespoke layout** → `RecentNotificationsCard`/`NotificationsBell` share a `NotificationContent` renderer (`src/components/dashboard/notification-display.tsx`) built around the same visual grammar as `ServiceRow` (`src/app/dashboard/projects/[id]/page.tsx`'s Services-tab row): a stack of independently-bordered mini-cards rather than one bordered panel wrapping a flat list. Each row shows a type-derived label (`NOTIFICATION_TYPE_LABEL`, keyed purely off `notification.type` — never parsed out of the free-text message) alongside the date/unread-dot, then the real message intact on its own line. Deliberately two lines, not three: the notification data model has no separate, safely-resolvable company/project/service field to justify a fabricated third line without adding new cross-referenced lookups or schema — do not invent one from the message string.
- **Team Lead's/Admin's "Team Workload" card is no longer forced into a side-by-side grid row with a taller sibling** → both Dashboards previously paired Team Workload against a taller stack (Client Health [+ Team Tasks by Status for Team Lead]) inside one CSS grid row, whose height is always governed by the tallest item regardless of `align-items` — meaning a short Team Workload (e.g. a 2-person team) always left a large blank area, even with `items-start`. Both Dashboards now render Team Workload full-width on its own row first, sized to its own content, with the remaining cards below it. `TeamWorkloadCard` gained optional `className`/`style` props to support this (matching every other Dashboard card's existing pattern).

**Why**: A visual/source design review (screenshots across all 3 roles × Dashboard/My Day/Week/Month, desktop + mobile, cross-checked against direct source reads) found Employee's Dashboard and My Day Today were near-duplicates (same header, same Notifications card, similar shape), while Team Lead's and Admin's Dashboards were missing Notifications and an attention signal entirely. Two real, source-confirmed defects came out of the same review: Admin's My Day Week/Month calendar defaulted to org-wide (`assigneeId: "all"`) instead of personal, inconsistent with every other role and with "My Day = personal by default"; and Team Lead's Dashboard had a genuine mobile horizontal-overflow bug at ~400px (`scrollWidth` 573 vs `clientWidth` 400), traced to two `lg:col-span-2` grid cards not getting `min-w-0` at the mobile breakpoint.
**Consequences**: `UpcomingDeadlinesCard` and `TeamActivityCard` both gained an optional `title` prop (defaults unchanged in spirit — `TeamActivityCard`'s default text changed from "Recent Team Activity" to "Recent Task Activity", `UpcomingDeadlinesCard`'s stays "Upcoming" unless a caller passes an explicit scope label). `useTaskFilters` gained an optional second `initialFilters` parameter — it only seeds the very first mount and is overridden by anything already persisted under a page's `storageKey`, so it never fights a viewer's own saved filter choice. Do not reintroduce a Notifications card on My Day, a personal Upcoming card on Employee's Dashboard, or a management Needs Attention strip on Employee's Dashboard — all three were deliberately, explicitly excluded from this change. Implemented on branch `feature/CD-196-dashboard-myday-information-architecture` — see `current-state.md` for current PR/merge status before assuming this is live on `main`.

### No AI/assistant attribution in Git history

**Decision**: Commits never include `Co-Authored-By: Claude`, `Co-Authored-By: ChatGPT`, or any other AI/model/assistant attribution trailer. Normal human authorship (the actual developer) is the sole Git author/committer.
**Why**: Explicit, repeated Product Owner instruction across this project's development.
**Consequences**: Any tooling or workflow that auto-inserts AI attribution trailers must be disabled/overridden for this repo. If you find a historical commit with such a trailer, it was a mistake later corrected (see the CD-162 branch-history cleanup, which rewrote two commits specifically to strip trailers while preserving content, order, and human authorship).

### Legacy "Project Template" bundle architecture retired at the schema/source level (CD-205)

**Decision**: The dormant whole-Project "Project Template" bundle (`project_templates`/`project_template_services`/`project_template_activities`, their RPCs/triggers/RLS/grants, and the corresponding dead `ProjectTemplatesProvider`/`use-project-templates`/mock+Supabase provider source code) is fully retired via a new forward-only migration and a source cleanup pass. This bundle layer had already been removed from the visible app in an earlier pass (see "Services/Activity Configuration correction," above) — that pass deliberately left the database objects and provider plumbing dormant rather than destroying them. This decision completes that retirement.

The **separate, older Service-recipe system** (`templates`/`template_tasks`/`template_checklist_items`, `apply_template`, `materialize_template_tasks`, `apply_service_template_to_project`, and the Company-detail "Apply template" flow) is explicitly **not** part of this retirement — a targeted dependency audit confirmed it is a genuinely live feature (real seed data, a real reachable UI button, real capability — checklist items, due-date offsets, expected-minutes estimates, recurrence inheritance — that the current `Activity.defaultTaskTitles`/"Quick Add" mechanism does not replace). It is preserved unchanged.

**Why**: An exhaustive read-only dependency audit (schema FK/cascade graph + source-code A/B/C/D classification, two independent research passes) found: zero inbound FK from any real Project/Workstream/Activity/Task/Checklist table into any of the three dropped tables (the only inbound FK anywhere in the schema pointing at either template system, `tasks.template_id → template_tasks(id) ON DELETE SET NULL`, belongs to the separate, preserved Service-recipe system); `create_project`/`create_client_project`'s `p_template_id` parameter was already optional and every current UI caller already omits it; and the bundle's own UI had already been fully removed in the prior pass. The one required companion fix: `admin_delete_activity` queried `project_template_activities` directly in its own delete-guard, and would have thrown a "relation does not exist" error on every future Activity deletion once the table was dropped — repaired in the same migration.

**Consequences**: `service_lines`, `workstreams`, `workstream_members`, `activities`, `departments`, `tasks`, `checklist_items`, `projects`, and `companies` are untouched. `create_project`/`create_client_project` keep their existing callable signature (`p_template_id` stays, as a deprecated/technical-compatibility-only parameter, default `null`) — a non-null legacy value now raises a clear exception rather than either erroring on a dropped table or silently doing nothing. The canonical future meaning of "Template" (the current Service catalog, `service_lines`) — not implemented by this decision — was implemented next, in Phase 1 (CD-206, see below). The Service-recipe system's own long-term fate (converge into that Template architecture once it reaches feature parity, or remain a permanent separate mechanism) is a genuinely open product question, not resolved here.

**Status**: implemented and merged (PR #5, merge commit `83bff9c`), migration applied to hosted Supabase and independently re-verified live (object absence/presence, exact function-body match, unaffected operational row counts). See `data-and-supabase.md`'s migration history for the exact migration, and `current-state.md` for live status.

### Phase 1 — Template workspace and terminology (CD-206)

**Decision**: The visible product term for the global Service catalog item and its per-Project instance changes from "Service" to "Template" (e.g. "Accounting," "Payroll," "Compliance" are now Templates). This is a **visible terminology and UX change only** — `service_lines`/`ServiceLine` (catalog) and `workstreams`/`Workstream` (per-Project instance) persistence, routes, RPC/RLS names, and internal component/identifier names are all deliberately unrenamed. See `domain-model.md`'s "Template vs. Service Line/Workstream" section for the full locked mapping.

Concrete scope, classified by meaning (not a blind find-replace) across a full terminology audit:
- **Admin navigation + catalog**: sidebar label "Services" → "Templates"; the catalog page moved from `/dashboard/admin/services` to `/dashboard/admin/templates` (307 redirect kept for the old bookmark); a **new per-Template detail page** (`/dashboard/admin/templates/[id]`) was added — the catalog previously had no per-row route at all. The detail page shows name, active state, description (new `TruncatedText` one-line-preview/"View more"/"Show less" component — no equivalent existed in the codebase before this), Activities ("View Activities," reusing the existing `ManageServiceActivitiesDialog` unchanged), and full editable Team Leads/Members (`MultiSelect`, unchanged component). The **list** page now shows staffing compactly via the existing `PeopleInline` component (avatar + first name + "+N", full-name tooltip) instead of the list's own raw `MultiSelect` chip stack — editing moved to the detail page. No new description field/migration was needed — `service_lines.description` already existed (`20260904110000_service_catalog.sql`).
- **Project-facing**: the Project detail "Services" tab, its summary panel, KPI tile, empty states, and "Add Service"/"Configure Activities" actions all became Template wording ("Add Template," "View Activities"). The Project-facing **"Global Service Staffing" display block was removed entirely** (from both the Project Templates-tab card and the Template/Workstream detail page's own Team tab) — display-only cleanup; the underlying global staffing data/model (`service_team_leads`/`service_employees`) is untouched and still shown, compactly, on the Template's own admin detail page. Legitimate Project-specific Lead/Team (`workstream.leadUserId`/`workstream.team`) was preserved and relabeled "Project Template Lead"/"Project Template Team."
- **Task List**: locked column set became **Task / Priority / Project-Template / Start Date / Due Date** — the visible Assignee column was removed (Assignee remains fully available as Task detail data, a List filter, and assignment functionality — only the column was dropped) and Start Date was added, reusing the already-existing `Task.startDate` field and the same `formatDueDateShort` helper Due Date already used. Board/Timeline/My Day/Planner were explicitly not touched (their own `showAssignee` grouping logic is unrelated and untouched).
- **Staffing terminology**: "Employees"/"Services Led"/"Works In Services" became "Members"/"Templates Led"/"Works In Templates" wherever they describe Template staffing (Admin catalog page, Admin User edit dialog). The underlying `employee` role name is unchanged — only the staffing-relationship label changed, never the role.
- **Activity catalog**: the "Suggested Tasks" label (tied to `Activity.defaultTaskTitles`) became "Tasks" — but only in this Admin Activity-catalog-edit context. The Task form's own, unrelated "Suggested: {Activity}" keyword-match feature was explicitly left alone (a different feature, same word), as was a third, unrelated "Suggested: {role}" badge inside the separate Apply-Template (Service-recipe) dialog.
- **Breadcrumbs**: no reusable breadcrumb component existed anywhere in this codebase before this phase (only one ad hoc, non-reusable "Company / Services" string). A new `Breadcrumb` component (`>` separator, representing only real navigation hierarchy) was added and used on the new Template detail page.

**Explicitly not part of this phase** (locked out-of-scope, tracked for later phases): no authorization/permission change of any kind (Admin-only catalog administration stays Admin-only; `canManageProjects`/`canConfigureWorkstreamActivities`/etc. untouched); no Project-creation redesign; no database-wide `ServiceLine`/`Workstream` rename; no Template cloning ("start from an existing Template," the locked future "A2" model); no Partner Brand/Activity decoupling; no Task status model change.

**Why**: Product Owner decision, following directly from the Phase 0/CD-205 retirement's own stated next step — the legacy "Project Template" bundle concept was retired specifically so "Template" could become the canonical name for the thing that already existed (the Service catalog), without a second, competing meaning of the word anywhere in the app.

**Consequences**: The separate, older "Service Template" recipe feature (`templates`/`template_tasks`/`template_checklist_items`, `apply_template`, the Company-detail "Apply template" button) is **explicitly unrenamed and unaffected** — its own use of the word "Service"/"Template" in its own copy was deliberately left exactly as-is, since renaming it would misrepresent a still-distinct feature. A targeted continuation audit closed the remaining genuine user-facing terminology gaps on Company detail, Settings/Workspace, Daily Updates, reports, dashboard summaries, and rare provider error paths. Residual "Service" strings are deliberately retained only where they are internal identifiers/persistence names, part of the preserved Service-recipe flow, or unrelated generic business prose. No new migration was required. No authorization behavior changed anywhere — verified by inspection, not just by omission, since no permission function, RLS policy, or RPC was touched.

**Status**: implemented and merged (PR #7, merge commit `ab9aa8f`). Product Owner Try-It-Yourself review approved (2026-09-23). See `current-state.md` for live status.

### Phase 2 — Project Overview redesign + KPI navigation (CD-207)

**Decision**: The Project detail page's Overview tab (`src/app/dashboard/projects/[id]/page.tsx`) is redesigned around one shared structure for every role (Admin/Team Lead/Employee) — never a role-branched layout. Role differences come only from existing permissions/edit affordances, never a different set of cards or a widened authorization surface.

Concrete scope:
- **Locked 5-tile KPI row**, each tile a real, keyboard-operable `<button>` that navigates to the matching Project tab via `handleTabChange` (never a raw `setTab` call, which is exactly what the previous tab/URL desync bug was — see below): **Templates** (`activeWorkstreams.length` → Templates tab), **Open Tasks** (`openCount`, narrowed to `myTasks.length` for Employees → Tasks tab), **Attention** (see below → Tasks tab), **Due** (see below → Tasks tab, period pills excluded), **Members** (`project.members.length` → Members tab, a KPI that didn't exist before this phase).
- **Attention** = unique (deduplicated) Tasks that are overdue OR have status Waiting, computed as one filter pass over one already-viewer-scoped array (`isTaskOverdue(t) || t.status === "waiting"`) — a Task matching both conditions is counted once by construction. Blocked is deliberately excluded from this one KPI's definition only; Blocked itself is untouched everywhere else in the app (status control, Board column, etc.) — no migration, no status-model change.
- **Due** = incomplete, non-overdue Tasks due within a compact Today/Week/Month period selector (default Today), reusing `src/lib/planner-dates.ts`'s existing local-calendar-date helpers (`todayDateOnly`, `parseDateOnly`, `startOfWeekMonday`, `startOfMonth`, `addDays`) — the same semantics My Day's own Week/Month views already use. No new date-comparison scheme was invented, `isTaskOverdue`'s own internal UTC-slice "today" was left untouched, and CD-193's broader date-normalization territory was not entered.
- **Administrative Details consolidation**: the former two separately-gated cards ("Project Details," visible to everyone, and "Administrative Details," Admin-only) are merged into one `AdministrativeDetailsCard`, same structure for every role, with zero field loss (description, Owner, Project Group, Start/End date, Client Since, Completed On/Archived On, Tags, Account Status, Partner Brand, Contract Start, Renewal Date, Contacts, Created by — every field from both prior cards is present). Only the *read-only render* gate widened from Admin-only to all roles; the *edit* affordances (header Edit button opening `CompanyFormDialog`, "+ Add contact," per-contact "Edit") stay `canManageProjects`-gated, unchanged. No new data fetch or authorization surface was introduced — `useCompany`/`useCompanyLookups` were already unconditionally called for every role before this phase; only what was rendered from that already-fetched data changed.
- **Tab/URL sync fix**: the audit found 5 call sites (inside the panels removed below) that called the bare `setTab(...)` state setter directly, bypassing `handleTabChange` (the one function that also pushes `?tab=` to the URL) — a real, confirmed bug where clicking "View Tasks"/"View Templates"/"View Members" from Overview changed the visible tab without updating the URL, so Back/Forward/refresh/deep-link could show a tab that didn't match what was last clicked. Fixed as a natural consequence of the redesign (every new KPI tile calls `handleTabChange`), not as a separate patch.
- **Project list row navigation**: `src/app/dashboard/projects/page.tsx`'s row (`ProjectTableGroup`) was a `role="button"`/`tabIndex`/synthetic-`onClick` `<div>` — functionally clickable/keyboard-operable already, but without real anchor semantics (no ctrl/cmd/middle-click "open in new tab," no hover URL preview, no visible focus ring). Converted to a real `<Link href={...}>`, reusing the exact wrapping pattern the Templates tab's own `ServiceRow` already established (nested interactive elements, e.g. the Trash-view "Restore" button, call both `preventDefault()` and `stopPropagation()` on their own `onClick`). The router-push-based `onOpenProject`/`openProject` indirection was removed as dead code once the `Link` provided native navigation.

**A scope decision made without a Product Owner stop**: the former `AttentionPanel`, `ServicesSummaryPanel`, and `TeamPanel` components (and the old, non-clickable 4-tile KPI row) were removed entirely rather than kept alongside the new KPI tiles. Reasoning: their information is fully subsumed by the new 5-tile KPI row (all three exposed a "View X" link to the same tabs the tiles now navigate to directly), and every one of the 5 `setTab`-bypass bug's call sites lived inside these three components — keeping them would have meant either duplicating the Attention definition in two places (a real risk of the two disagreeing) or leaving the bug in place. This was judged a direct, non-ambiguous consequence of the locked spec's own stated goals (avoid duplicated Project metadata cards, one shared structure per role), not a genuine open product question — flagged here for visibility rather than treated as requiring a stop.

**Why**: Product Owner-scoped Phase 2 of the Project-module redesign series (following Phase 0/CD-205's System A retirement and Phase 1/CD-206's Template terminology rename) — locked KPI set and Attention/Due definitions were specified directly; the tab/URL sync and card-clickability fixes were audit-discovered defects explicitly called out as in-scope.

**Consequences**: `formatShortDate` (a `page.tsx`-local helper) and the computed values `statusCounts`, `nextDueTask`, `myOverdueCount` (a raw `.toISOString().slice(0, 10)` comparison — removed, not propagated), `myNextDueTask`, `overdueCount`, and `isTeamLead` were all removed as dead code once their only consumers (the removed panels/old KPI row) were gone. `serviceLineDisplayName`/`PeopleInline` imports and the `serviceLines` local from `useCompanyLookups()` became unused in `page.tsx` for the same reason and were removed. Nothing in `src/lib/data/permissions.ts` changed — `canManageProjects` still gates every mutation the same way it did before; only what non-mutating data is rendered for a non-Admin viewer widened. Explicitly out of scope and untouched: CD-193, Project creation/edit redesign, Template cloning, Partner Brand decoupling, staffing/authorization redesign, any Blocked→Waiting status migration, contract-work generation.

**Status**: implemented and merged (PR #9, merge commit `997c3ce`), TypeScript/ESLint/`git diff --check` all clean, all 4 provider builds (mock/supabase-auth/supabase-core/supabase) pass, isolated interactive QA (Admin/Team Lead/Employee, responsive) passed. Product Owner manual review approved (2026-09-23). See `current-state.md` for live status.

### Phase 3 — Project creation, ownerId-based management authority, true Template snapshots, Partner Brand decoupling (CD-208)

**Decision**: Four previously-unresolved product questions, surfaced by this phase's own pre-implementation audit (see the audit report on CD-208), were explicitly resolved by the Product Owner before implementation began:

1. **Project-management authorization boundary**: `Project.ownerId` is now the write-authorization boundary for a Project record. `canManageProjectRecord(viewer, project) = isSuperadmin(viewer) || (isSupervisor(viewer) && project.ownerId === viewer.id)` — mirrored server-side by a new `can_manage_project(target_project_id)` SQL function. This is deliberately narrower than `canAccessProject` (read) — direct-report visibility, `project_members`/`projectRole` (data-only), global Template staffing ("Works In Templates"), and `workstream.leadUserId` ("Project Template Lead," Template-instance-scoped) all grant zero Project-management authority. A Team Lead who creates a Project always becomes its owner (`create_project`'s Supervisor branch forces `owner_id = auth.uid()`, never trusting a client-supplied value) — this is **not** a new "Primary Team Lead" model (explicitly deferred to Phase 4); it's the existing, already-present `ownerId` field pressed into service as the Phase 3 bridge. This exact question had been explicitly, repeatedly deferred throughout the project's history — see `docs/admin-foundation-user-service-architecture.md`'s Stage 0 corrections ("a future, explicitly-approved Project/Service validation phase will define that meaning").
2. **True Template/Activity snapshot semantics**: canonical Template application now freezes the applied Template's Activity structure (name/description/`defaultTaskTitles`/position) onto the Project's own Workstream at the moment of application — a later edit to the global catalog no longer retroactively changes an already-created Project. Previously this was a live FK join (`workstream_activities` stored only `{workstream_id, activity_id}`; every read live-joined the current `activities` row). See "Snapshot implementation" below for the schema.
3. **Partner Brand becomes Project-specific**: `projects.partner_brand_id` (nullable, independent of `companies.brand_id`) — two Projects under the same Company may now carry different Partner Brands. Backfilled once from the owning Company's Brand at migration time; no ongoing sync in either direction afterward.
4. **Canonical Template Activities decoupled from Partner Brand**: previously real, structural coupling (`departments.brand_id not null`, actively filtering which Activities were selectable across 7+ UI surfaces) — a canonical Template's Activity structure is now Brand-independent. A prior project audit (`docs/project-level-product-architecture.md`) had explicitly scoped full decoupling as "a real Activity Catalog redesign, out of scope" for its own phase; the Product Owner explicitly approved doing it now, scoped narrowly (see "Brand decoupling implementation" below).

**Snapshot implementation**: `workstream_activities` gained frozen columns (`name`, `description`, `default_task_titles`, `position`) populated at application time (`create_workstream`, "Configure/Add Activities"), a surrogate `id` primary key (replacing the old `(workstream_id, activity_id)` composite, since `activity_id` needed to become nullable), and `activity_id`'s FK changed from `on delete cascade` to `on delete set null` (a snapshot must survive even a source Activity later being deleted — `admin_delete_activity`'s own usage guard already prevents this in the normal RPC path, but the schema itself no longer depends on that guard for data safety). `activity_id` stays as a pure lineage pointer — `tasks.activity_id`/`project_issues.activity_id` are explicitly untouched, still pointing at the live global `activities` table (a Task's own Activity link is a stable identity reference, not part of what needed to snapshot). `workstreams.name`/`description` needed **no schema change at all** — `name` was already frozen at write-time by the client (`deriveWorkstreamName`), it was only the READ side (`workstreamDisplayHeading`) that defeated the freeze by preferring a live-joined Service Line name; that read-time preference was removed (the function now just returns `name`), and a one-time migration re-froze every existing Workstream's `name` to its then-current live-displayed value so nothing visibly changed at the moment of migration.

**Brand decoupling implementation**: `departments.brand_id` became nullable. Going forward, the Department scoping a Service Line's canonical Activities has `brand_id = null` (a single, Brand-independent container per Service Line, enforced by a new partial unique index). A migration consolidates each Service Line's existing Brand-scoped Departments into one canonical Department, re-pointing their Activities onto it (Activity ids unchanged — only `department_id` moves, so `workstream_activities`/`tasks`/`project_issues` references are unaffected) — the migration aborts loudly rather than silently merging if it ever finds a cross-Brand Activity-name collision for the same Service Line (none found as of the audit backing this: only one seeded Brand had any Departments/Activities at all). Every canonical Template/Project Activity-picker consumer (`AddServiceActivitiesDialog`, `ProjectServicePicker`, `WorkstreamFormDialog`, `useWorkstreamActivities`) stopped passing a `brandId` to `useActivityCatalog`/`listDepartments`; three Category-B consumers unrelated to canonical Template application (`AddSectionDialog`/client reports, `AddServiceDialog`/Accomplishments Report, `AddManualEntryDialog`/daily updates) had their own `brandId` argument dropped too, since the underlying Activities they browsed moved to the canonical Department and their own brand-scoped query would otherwise have silently started returning nothing — this is a mechanical "keep the call working," not a redesign of those features. The Admin Template-catalog's own Activity-creation flow (`admin_create_activity_for_service_line`) still asks for a Brand and still creates Brand-scoped Departments for NEW catalog Activities — this was deliberately left as a smaller, separate follow-up rather than folded into this phase, since it's an Admin-only administrative path, not part of what blocks Team Lead-facing Project creation/Template application.

**New RPCs** (all `SECURITY DEFINER`, explicit `search_path`, `can_manage_project`-gated where relevant): `can_manage_project(uuid)`, `apply_project_templates(project_id, templates jsonb)` (atomic multi-Template application — reused by both "Add Template" and, via a nested call within the same transaction, `create_project`/`create_client_project`'s own creation-time Template application, so a failed Template application rolls back the whole Project creation), `update_project_record(...)` (replaces a direct client-side `.update()` on `projects` — enforces field-level protection for Name/Owner/Partner Brand server-side, never trusting the client; `projects_update` RLS itself stays Superadmin-only, deliberately not widened), `create_project_group(name)` (Admin-or-Supervisor, replacing a direct-table insert that RLS still restricts to Admin). `create_project`/`create_client_project` gained `p_partner_brand_id` and `p_templates jsonb` — **never** repurposing the retired System A's `p_template_id` parameter, which stays exactly as CD-205 left it (a non-null value still raises "Legacy Project Templates are no longer supported").

**Three real bugs found by interactive QA during this phase, all fixed before this checkpoint** (see `troubleshooting.md` for the second and third ones' full writeups, since both are durable gotcha classes, not just one-offs):
1. **Snapshot leak in `useWorkstreamActivities`**: the hook every Activity picker (Task form, Quick Add, the Workstream detail page) reads from was cross-referencing the Workstream's own frozen `activities` ids against a **fresh live fetch** of the global catalog and returning those live objects — silently defeating the snapshot for every consumer of this hook even though `workstream_activities`' own frozen columns were correct. Fixed to read `workstream.activities` directly, no live catalog fetch at all.
2. **`canAccessCompany`/`visibleCompanyIds` mock/hosted parity gap**: the hosted `can_access_company` SQL (Phase 8B, `20260815110000_company_access_via_project.sql`) already grants Company access via an accessible Project, not just an explicit staff assignment — the app-layer/mock version was never updated to match when that migration was written, and stayed invisible until Phase 3 made Team-Lead-owned Projects routine. A Team Lead who owned a Project under a Company they weren't separately assigned to got a silent `company: null`, hiding the Administrative Details card and the "Add Template" button. Fixed by widening the app-layer functions to mirror the hosted SQL exactly; the Supabase provider needed no change since hosted RLS was already correct.
3. **`useProject(id)` didn't clear its data on route-key change**: `isLoading`/`notFound` reset synchronously when `id` changed, but the `project` object itself stayed at the previous Project's value until the new fetch resolved — a client-side nav from one Project straight to another could in principle render a role/ownership-gated control (like "Add Template") against the OLD Project's data for a frame. This surfaced during CD-208 QA as a screenshot that appeared to show a Team Lead's "Add Template" button on a Project they didn't own, immediately after navigating there from one they did. Not an authorization bypass at any point — `apply_project_templates`/`update_project_record` (and the mock equivalents) independently re-validate ownership server-side on every call, so the worst case was ever a stale button that would fail on click. Fixed in `useProject` only; `useWorkstream` has the identical pattern but predates Phase 3 and wasn't implicated by this finding, so it was deliberately left as a separate follow-up rather than folded into this diff. A dedicated same-day browser recheck (DOM button-count checks across a full Project-to-Project SPA navigation plus a hard reload) reproduced **zero** flashes of the button at any point, and found a structural reason why: this app has no in-app link that navigates directly between two Project pages at all — the only path is through the Projects list, a different route, so `useProject` always fully unmounts/remounts rather than experiencing an in-place `id` change. The fix is correct for the race it targets, but that race isn't reachable through any current UI affordance, so the original screenshot's precise cause remains unknown. See `troubleshooting.md` for the full recheck writeup.

**Why**: the natural next phase of the Project-module redesign series (Phase 0/CD-205 System A retirement, Phase 1/CD-206 Template terminology, Phase 2/CD-207 Overview redesign) — Team Lead Project creation was the ticket's own headline requirement, and implementing it honestly required finally resolving the ownership-authority question this project's history had repeatedly, deliberately deferred.

**Consequences**: `Project.partnerBrandId`/`ProjectWithRelations.partnerBrand` are new; the Administrative Details card's "Partner Brand" field now reads `project.partnerBrand`, never `company.brand`. `Workstream.brandId`/`WorkstreamWithRelations.brand` became nullable (a Project/Company with no Brand set no longer blocks Template application — `create_workstream`'s old hard "this client has no Brand set yet" guard was removed). `Department.brandId` became nullable in the type system too. Member staffing (`ProjectFormDialog`'s Members section) stays Admin-only in the UI — Team Lead gains no new staffing rights in Phase 3, per its own explicit boundary. Explicitly out of scope and untouched: A2/global Template cloning (still deferred), Phase 4's broader staffing/authorization model (Primary/Additional Team Leads, per-Template Lead permissions), Phase 5's Blocked→Waiting retirement, Phase 6's contract-model redesign, CD-193, System B (`templates`/`template_tasks`/`apply_template`/Company's "Apply template" button — all byte-for-byte unchanged).

**Status**: implemented on branch `feature/CD-208-project-creation-unified-editing` (based on `main` at `57021cd`), TypeScript/ESLint/`git diff --check` all clean, all 4 provider builds pass. Product Owner reviewed and approved the implementation (2026-09-24). All 6 migrations (the original 5, plus the follow-up `20260930160000_phase3_authorization_hardening`, see below) are applied to hosted Supabase — migration history and postflight verified (see `data-and-supabase.md`). In Code review; not merged, not deployed. See `current-state.md` for live status before assuming any of this has merged.

**Post-migration authorization hardening (2026-09-30)**: a final hosted authorization pass, after the original 5 migrations were live, found 3 residual gaps where Service/Workstream mutation was still gated by a READ/visibility predicate (`can_access_project`) or the pre-Phase-3 model instead of the new owner boundary (`can_manage_project`): (1) `create_project`'s Supervisor path could seed `project_members` via `p_member_user_ids` through its SECURITY DEFINER privilege, bypassing the Admin-only RLS on that table — broader Project staffing is Phase 4's territory, so a non-Admin caller supplying any members now gets a clear exception (`create_client_project` is covered automatically, since it delegates into `create_project`); (2) `create_workstream`'s Supervisor branch authorized Service creation via `can_access_project(p_project_id)` instead of `can_manage_project(p_project_id)` — a non-owner Supervisor could otherwise create a Service on a Project they merely had read access to; (3) the `workstreams_insert` and `workstream_activities_write` RLS policies still used the pre-Phase-3 model (any Supervisor regardless of ownership, an Employee-as-lead branch, or `manages_user`+`can_access_project`) — both replaced with `can_manage_project`-based checks, Employee direct table INSERT now denied outright. All closed additively in one migration (`20260930160000_phase3_authorization_hardening.sql`); none of the original 5 migrations were edited.

### Phase 4 — Project staffing: Additional Team Leads (CD-208 follow-on, no Jira ticket yet)

**Decision**: Project.ownerId (Primary Team Lead) stays exactly as Phase 3 left it — single, Admin-only to reassign. A Project may additionally have 0..many Additional Team Leads via a new dedicated relation, `project_team_leads(project_id, user_id)`, each getting the exact same normal Project-management authority as the Primary TL (via `can_manage_project`/`canManageProjectRecord`), with the sole exception that changing `owner_id` itself remains Admin-only. Deliberately NOT layered onto `project_members`/`project_role` (both stay descriptive-data-only, never authorization-bearing) — a dedicated relation was chosen specifically to avoid conflating "Team Lead" and "Member" into one row shape, per the Phase-4 audit's own risk analysis of that alternative. Eligibility (active Supervisor, never the Project's own owner) is enforced at the database level via a `BEFORE INSERT` trigger, not just the RPC/UI layer. Project Members gained two new narrow RPCs (`add_project_member`/`remove_project_member`) usable by Admin or any authorized Team Lead, incremental (not a bulk replace) and separate from the existing Admin-only bulk `memberUserIds` sync (unchanged). Two residual gaps the audit found were closed alongside this: `canConfigureWorkstreamActivities` (app/mock) had drifted out of sync with the hosted `workstream_activities_write` RLS Phase 3 had already hardened; `workstream_members_write` RLS itself had never been touched by Phase 3 at all and still used the pre-Phase-3 broad-Supervisor model. All staffing mutations (Additional TL add/remove, Member add/remove, Workstream Lead/Team reassignment via the new `update_workstream_staffing` RPC) require the Project to be Active — enforced in both the RPCs and, as defense-in-depth, directly in RLS (no Admin exception, matching `workstream_activities_write`'s own established precedent). `workstreams.lead_user_id` stays exactly one Lead per Workstream — no Additional Workstream Leads introduced.

**Consequences**: `ProjectWithRelations.additionalTeamLeads: User[]` is new (mirrors `members`'s own resolved-object shape); `canManageProjectRecord`/`canAccessProject`/`canAccessCompany`/`canAccessWorkstream`/`canConfigureWorkstreamActivities` all gained an `additionalTeamLeadUserIds`-aware parameter shape, propagated to every call site across both providers (mock and Supabase) — a systematic repo-wide search confirmed no call site was left constructing the old, narrower shape. `update_project_record` now atomically removes a redundant Additional-TL row when Admin reassigns `owner_id` to someone who already held one; the previous owner is never auto-converted to Additional TL. Workstream/Service Lead-Team staffing has a UI entry point now too: `WorkstreamFormDialog` gained a `staffingOnly` mode (a "Manage Staffing" button, shown only for a non-Admin authorized Project Team Lead on an Active Project) that hides every field except Lead/Team, reuses their existing target-eligibility-scoped pickers as-is, and submits through `update_workstream_staffing` instead of `updateWorkstream` — Admin's existing full-edit dialog is untouched and still works unchanged. Global Template staffing (`service_team_leads`/`service_employees`) is completely untouched, as is System A/B, Partner Brand, and the Template/Activity snapshot architecture.

**Status**: implemented on branch `feature/phase-4-project-staffing-authorization` (stacked on CD-208's checkpoint commit `fda0cfe`, since PR #11 was still open/unmerged when this began). Three new local-only migrations (`20260930170000_phase4_project_staffing_foundation.sql`, `20260930180000_phase4_workstream_staffing_alignment.sql`, `20261001090000_phase4_staffing_candidate_directory.sql`). `tsc`/ESLint/`git diff --check`/all 4 provider builds (mock/supabase-auth/supabase-core/supabase) all pass clean. Interactive QA (7 role/lifecycle scenarios) and a direct provider-call security test (9/9 assertions, bypassing the UI entirely) both passed, run against an isolated mock-mode copy — one real bug found and fixed: the Additional Team Lead/Project Member candidate pickers inherited `listAssignableStaff`'s team-scoping (backed by `profiles`' own RLS, not just an app filter), which in this app's actual 2-Supervisor seed org meant neither Supervisor could ever add the other as an Additional Team Lead through the UI — confirmed via QA's own positive-control direct-call test that the backend never had this restriction. Fixed with a new, narrow, unscoped directory RPC (`list_project_staffing_candidates`) — see `data-and-supabase.md`'s migration entry for the full writeup. **Product Owner manually tested Phase 4 and approved the implementation** (2026-10-01). All 3 migrations applied to hosted Supabase and independently postflight-verified (schema/RLS/grants/function bodies read directly from hosted, zero data-row changes across every counted table, System A/B unaffected) — see `current-state.md` for the full postflight record. See `current-state.md` for the live Git/Jira checkpoint status.

### Phase 5 — Retire the Task status Blocked in favor of Waiting (CD-214)

**Decision**: `Blocked` is retired from `TaskStatus`; `Waiting` is the sole remaining status that requires a `statusReason`. Five Product Owner decisions, surfaced by this phase's own pre-implementation audit, were locked before implementation began:
1. **Legacy URL/filter compatibility is read-only, one-directional**: a stale `?status=blocked` link, sessionStorage entry, My Day bucket selection, or Saved View transparently behaves as `waiting` on read/apply. New links/saved state generated by the app never produce `blocked` again.
2. **Attention is deduplicated**: unique Tasks that are overdue OR Waiting, a Task matching both counted once — already the Project-detail KPI's existing formula (CD-207); the Dashboard's separate "Needs Attention" staff strip (`needs-attention-strip.tsx`) previously implemented the *opposite* rule (counted Blocked, ignored Waiting) and is now aligned to the same definition.
3. **Projects-list Team Lead table's separate Blocked column is removed**, folded into the existing Waiting column — Waiting keeps its own warning (not destructive/red) styling; Blocked's styling is not transferred.
4. **No new Task-status history/audit subsystem.** Existing rows may normalize Blocked → Waiting; historical decision/QA records (this entry, prior phases' decisions, dated `references/` screenshots) stay untouched as historical truth, never rewritten.
5. **Write compatibility is deliberately different from read/filter compatibility**: a stale caller attempting to WRITE `status: "blocked"` is rejected outright (never silently converted) — at the UI (type removed from the union), the mock provider (new runtime `isTaskStatus` membership guard, since TypeScript alone is not runtime enforcement), and the hosted database (`tasks_status_check` CHECK constraint tightened to 5 values, `update_task_status`'s own redundant allow-list updated to match).

**Audit finding carried into scope**: the pre-implementation audit found the two Attention-KPI implementations actively disagreed (Project-detail: overdue-or-Waiting, Blocked excluded; Dashboard staff strip: overdue-or-Blocked, Waiting excluded) — reconciling them (Decision 2) is a real, intentional behavior change: a previously-Blocked, non-overdue task now counts toward the Project-detail KPI for the first time, and a previously-Blocked staff member now appears in the Dashboard strip via Waiting instead of via the no-longer-possible Blocked match.

**Shared status domain consolidation**: the audit also found the "needs a reason" predicate and a `STATUS_ORDER`-equivalent array independently duplicated across roughly a dozen files, with zero shared derivation point. Phase 5 introduced `src/lib/data/task-status.ts` as the single canonical source: `TASK_STATUS_ORDER`/`ACTIVE_TASK_STATUS_ORDER` (the latter excluding `canceled`, reused by both the Task Board and My Day's bucket set), `isTaskStatus` (the runtime membership guard), `taskStatusRequiresReason`, and `normalizeLegacyTaskFilterStatus`/`normalizeLegacyTaskFilterStatusOrAll` (the FILTER/READ-only legacy compatibility mapping — explicitly never used on a Task write path). Every duplicated copy found by the audit was migrated to import from this module rather than left as a parallel literal.

**Consequences**: `TaskStatus` drops from 6 to 5 values. `tasks.status_reason`/`Task.statusReason` is unchanged (single shared column, no schema change there). `task-status-donut.tsx` (previously re-literaling its own color/label/order maps despite a comment claiming it "never drifts") now imports the canonical `STATUS_COLOR_VAR`/`TASK_STATUS_SELECT_ITEMS`/`TASK_STATUS_ORDER` — closing that drift risk as part of this phase's cleanup, not deferred. Saved Views (`saved_views.filters` jsonb, hosted) gain a write-boundary normalization in both providers' `createSavedView` (filters are otherwise immutable after creation — there is no separate "edit an existing saved view's filters" path) and a read-time normalization in `saved-views-bar.tsx`'s apply path; the migration below also defensively backfills any existing hosted row, though the pre-migration audit found zero affected rows. `enforce_task_invariants`/`update_task_status` were redefined from their current (not original Phase-1) hosted bodies, preserving every unrelated invariant (archived-Workstream guard, inactive-Activity gate, the still-needed legacy reason-gap bypass for 2 named historical rows, authorization, notification fan-out) byte-for-byte. `create_task` is deliberately left unmodified — it never independently validated status membership before this phase either, and the tightened CHECK constraint alone closes that path.

**Explicitly out of scope and untouched**: Phase 6, A2, CD-193, global Template edit authorization, frontend production deployment, and a separate, independently-confirmed pre-existing defect found incidentally while auditing Task-status defaults — the System B `materialize_template_tasks()` RPC still hardcodes the stale pre-Phase-1 literal `status = 'todo'`, which no longer satisfies even the *pre-Phase-5* CHECK constraint (hosted `'todo'` was never a valid value after `20260908090000_task_status_model_phase1.sql`). This is unrelated to Blocked/Waiting and was not fixed here — flagged for a separate ticket.

**Status**: implemented on branch `feature/CD-214-retire-blocked-task-status` (created fresh from `origin/main` at `6ef8b7d`, the Phase-4 merge commit — not stacked on any unmerged branch). One new local-only migration, `supabase/migrations/20261001160000_phase5_retire_blocked_task_status.sql`. `tsc`/ESLint/`git diff --check`/all 4 provider builds (mock/supabase-auth/supabase-core/supabase) all pass clean. Non-hosted interactive QA (Admin/Team Lead/Employee, run against an isolated mock-mode copy) and a direct mock-provider-call test (status-membership rejection, reason-requirement lifecycle, Saved View write-boundary normalization, and the Attention dedup math with an explicit proof that naive addition would double-count) both passed — see `current-state.md` for the full QA record. **Hosted migration NOT applied** — awaiting Product Owner manual QA before the hosted-apply/checkpoint sequence.

### Phase 6 — Project contract-period model (CD-215/CD-216)

**Decision**: A pre-implementation audit (read-only, covering the existing Company/Project date fields, the retired `renew_project` feature, and the live-but-partly-orphaned rolling-duration contract pair) surfaced genuine architectural ambiguity; the Product Owner then locked the following before implementation began, and split the work into two tickets:

1. **Contract ownership**: operational/current contracts belong to **Project**, never Company. Company remains master/client data — no Company-level annual-period table exists or is planned.
2. **Three distinct date facts, not two**: Company `contractStartDate` (original client relationship start) and Project `contractStartDate` ("Client Since" — the original Project/engagement start) are genuinely independent facts on independent tables, despite the identical column name — a documented hazard class for this codebase (an earlier, analogous mixup between contract-term and work-timeline dates on Project itself already required its own corrective migration, `20260902120000_project_level_start_end_date_correction.sql`). Neither advances on renewal; post-creation correction of either is Admin-only.
3. **`companies.renewal_date` is preserved for compatibility only** — not dropped, not read as any Project's current contract.
4. **`projects.contract_months`/`projects.contract_end_date`** (the pre-existing rolling-N-month-duration pair, with its own "suggested end date" UX) **are preserved, untouched, but are no longer the authoritative annual-contract model.** `project_contract_periods` (new, Phase 6A) is authoritative going forward.
5. **Calendar-year period model**: every recorded period ends December 31 of its own start year (`2026-05-04 → 2026-12-31`; `2026-01-01 → 2026-12-31`) — not the rolling-duration model the legacy fields implemented. A renewal period always starts the January 1 immediately after its predecessor's end.
6. **History truthfulness**: `project_contract_periods` rows represent actual recorded business periods, never mathematically-generated guesses — directly continuing an already-established principle in this exact area (`20260815090001_projects_backfill.sql`'s own header: "CONTRACT DATES ARE NEVER FABRICATED"). No historical periods are backfilled from an old Client Since date merely because it exists.
7. **Renewal is Phase 6B/CD-216** — recording a *successor* period, the "Renew Contract" UX, Contract History management UX, automatic renewal, and renewal notifications are all explicitly deferred. Phase 6A establishes only the schema, the read surface, and the one "record the first period" mutation boundary.
8. **No Project duplication, ever** — the already-locked invariant behind `renew_project`'s own retirement (`20260908140000_project_lifecycle_authoritative_hardening.sql`: *"no annual duplicate Project/Client creation"*) carries forward unchanged. Contract-period changes have zero automatic effect on Templates/Services/Activities/Tasks/checklists/staffing/Partner Brand/Tags/Project Group/lifecycle status.
9. **Company → Project cardinality stays open**: no `UNIQUE(projects.company_id)` is added. The schema remains capable of one Company with several genuinely distinct Projects/engagements — annual renewal must simply never be the reason a second one is created.
10. **Authorization**: viewing contract data follows ordinary `can_access_project`. Contract-period *writes*, and post-creation *correction* of Company Contract Start / Project Client Since / the legacy contract-term pair, are all Admin/superadmin-only — narrower than the usual `canManageProjectRecord` boundary (which includes Team Leads for most other Project data), a deliberate, audit-flagged exception for contract fields specifically.

**Phase 6B (CD-216) additional locked decisions**, made once Phase 6A's foundation was merged:

11. **Renewal is manual only** — no automatic renewal, no `pg_cron` schedule, no hidden background behavior, no renewal reminders/notifications. Every mutation requires a direct RPC call from an authenticated Admin session.
12. **Renewal lifecycle eligibility**: a contract may be renewed only while the Project is Active or On Hold. Completed/Canceled/Archived/Trash all reject renewal outright; Reactivation never automatically creates or restores a contract period — a later renewal still requires an explicit Admin action.
13. **Early renewal is allowed, skipped-year auto-jump is not**: an Admin may record next year's renewal before the current period has expired (the prior period remains "Current" until its own `period_end`; the new one renders "Upcoming" until its own `period_start`) — but a renewal always extends from the current leaf by exactly one year. If the latest recorded period is several years stale, renewing creates the very next year only, never jumps ahead to "catch up" to the present; a genuine multi-year gap is a future business-rule decision, not something this feature silently papers over.
14. **The initial period is not a renewal**: a Project with zero recorded periods needs `create_initial_project_contract_period` (Phase 6A, unchanged) — reused, not reimplemented. The UI never calls this action "Renew Contract" (it has no history to renew); it also carries no lifecycle gate of its own, since recording a first truthfully-known period is history maintenance, not a lifecycle transition.
15. **Narrowest-safe correction model** — explicitly NOT arbitrary historical editing:
    - An Admin may remove ONLY the current leaf period in a Project's chain (a period with a successor is rejected outright — later leaves must be removed first, one at a time, so the chain can never be left disconnected); removing a Project's sole root period is allowed.
    - An Admin may correct the root period's `period_start` ONLY while it remains the Project's sole recorded period (no successor exists yet) — `period_end` is always recomputed server-side, `created_at`/`created_by` are never touched, and the correction is rejected outright once any renewal history exists.
    - A renewal successor's own dates are never independently editable — there is no "Edit renewal dates" action. A mistakenly-recorded renewal is corrected by removing that leaf, then renewing again when appropriate.
    - Lifecycle status never blocks either correction — correcting mistaken history is independent of whether the Project is currently renewal-eligible.
    - Both corrections are Admin/superadmin-only; Team Lead and Employee may never invoke either one.
16. **Contract History visibility**: visible to every legitimate Project reader (Admin/Team Lead/Employee, per ordinary `can_access_project`); only the mutation affordances (Renew Contract, the per-period overflow menu) are Admin-only. There is no separate Company-level Contract History.
17. **Display state stays derived**: Past/Current/Upcoming render fresh from today's date and the period's own `period_start`/`period_end` every time — no `is_current`/`status`/`renewal_status` column is ever added to `project_contract_periods`.

**Why**: the audit found the current system already had a partial, rolling-duration contract mechanism (with its own "suggested end date, user can override" UX) sitting alongside a fully-retired annual-Project-duplication mechanism (`renew_project`) and two confusingly-named-but-distinct Company/Project `contractStartDate` columns — none of which matched the stated calendar-year-period target model. Rather than guess at a reconciliation, the audit surfaced the ambiguity directly; the Product Owner's decisions above resolve it without discarding any existing data or silently fabricating history.

### CD-217 resolution — Project-level Apply Template + a merge-path authorization hardening

**Decision**: Keep Company administration (`src/app/dashboard/companies/[id]/page.tsx`) Admin-only, unchanged — the Product Owner explicitly declined to widen it. Instead, Admin and a **Project-authorized** Team Lead (the Project's owner or an Additional Team Lead — never "any Team Lead") may Apply an existing System-B Template from the **Project workspace**. Unrelated Team Lead and Employee may not. Global Template administration (create/edit/delete/configure) stays Admin-only throughout, untouched — Apply-Template authorization is never conflated with global Template-administration authorization.

**Implementation**: a new "Apply Template" button on the Project workspace's Templates (Services) tab, next to the existing "Add Template" (manual Service-Line-plus-Activities attach, a different, Task-less mechanism, left untouched). Reuses `ApplyTemplateDialog` — parameterized with an optional `project` prop rather than forked into a second template engine — and the Project page's own existing `canManageProjectRecord` boundary (the same one gating every other Project-management action on that page), not a new or broader check. Reuses the existing `apply_service_template_to_project` RPC/`ApplyTemplateInput.projectId` branch, both already present in the codebase from an earlier, never-wired-up pass — no new RPC, no schema change.

**Authorization hardening found and fixed in the same pass**: auditing `apply_service_template_to_project` for this feature's own authorization requirement found its **merge-into-an-existing-Service branch had no authorization check at all** — only the create branch was protected (indirectly, via its delegation to `create_workstream`, which does enforce `can_manage_project`/`canManageProjectRecord`). Any authenticated caller — including Employee, or a Team Lead with no relationship to the Project — could reach the unprotected merge branch simply by naming a Project/Template pair where a matching Workstream already existed, and silently insert `workstream_activities` rows. This was reachable only via a direct RPC call before this ticket (no UI had ever called this function), but this ticket's own new UI would otherwise have made it live-reachable through the product. Fixed by adding one check, `can_manage_project(p_project_id)` (hosted) / `canManageProjectRecord(viewer, project)` (mock), before the merge/create branch split, so both branches now share the single boundary the create branch always relied on — never a new or different authorization model, and never broadened beyond what `create_workstream` already enforced.

**Why**: the Company-detail page's own page-level Superadmin-only gate (see the prior entry) predates this ticket and covers more than just Apply Template (Company edit, Contacts, Create Project) — widening it was a bigger, separate decision the Product Owner chose not to make. The Project workspace, by contrast, already has a proven, narrower, per-Project authorization boundary (`canManageProjectRecord`) in active use for exactly this class of action ("Add Template" already lives there), making it the natural, minimal-surface home for this capability. The merge-path gap was found, not assumed — direct source inspection proved the create branch's protection was real (delegated to `create_workstream`) while the merge branch's was entirely absent, a defect in the one function itself rather than a design choice to revisit.

**Consequences**: `ApplyTemplateDialog` gains an optional `project` prop; when given, the dialog hides the (ignored-server-side-anyway) Service-name field, shows the Project in its header/preview, and passes `projectId`/`activityIds: []` through to `applyTemplate`. No change to the legacy Company-only path's own behavior. `mockWorkstreamsProvider.createWorkstream`'s now-dead `canCreateWorkstreamInProject` import was removed from its one remaining call site (replaced by `canManageProjectRecord`); the function itself is left defined (historically referenced by name elsewhere in `docs/`) but is no longer called anywhere.
