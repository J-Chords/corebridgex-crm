# Database & Supabase

## Hosted vs. local — don't confuse the two

`supabase/config.toml` is the **local Supabase CLI dev-stack config** (`supabase start`) — its `site_url = "http://127.0.0.1:3000"` and `127.0.0.1` ports are local-only defaults, not the hosted project's actual settings. The **hosted** Supabase project's real configuration (Auth Site URL, redirect URLs, production connection details) lives in the Supabase Dashboard, outside this repo, and is **not verifiable from repository evidence alone**. If you need to confirm hosted Auth settings, check the Dashboard directly — don't infer them from `config.toml`.

## Migration workflow

Migrations live in `supabase/migrations/`, applied **manually** against the hosted project (there is no CI/CD automation — see `deployment.md`). The established pattern for a hosted change, followed throughout this project's history: write the migration → apply it directly against hosted → verify parity (local migration list matches what's actually applied) → verify the specific guarantee it introduces, often via a rollback-only transaction proof against hosted before trusting it live.

**Known gotcha**: a migration's own header comment can go stale. Two 2026-09-11 migrations (`20260911090000_workstream_lifecycle_and_duplicate_prevention.sql`, `20260911100000_archived_workstream_task_guard.sql`) still say **"NOT YET APPLIED TO THE HOSTED PROJECT"** in their own file header — but both were in fact applied and verified against hosted Supabase during CD-162's final deployment (see `current-state.md`). Nobody went back to edit the comment after deploying. **Don't trust a migration file's header as a live status indicator** — check `current-state.md` or query the hosted schema directly.

## RLS pattern

See `authorization.md`'s RLS section for the two-tier pattern (direct-grant-plus-RLS-policy for simple CRUD vs. `SECURITY DEFINER` RPC-only for complex/stateful mutations). The RPC pattern is used specifically where an operation is genuinely sequential/stateful and needs atomicity — e.g. the one-active-timer-per-user rule, pause/resume chains, multi-table Project+Members creation, or a delete that must check several dependency tables under a row lock.

### Contract renewal + Contract History correction (Phase 6B, CD-216)
One migration, **applied to hosted Supabase, postflight-verified** (Product Owner manually approved the local implementation 2026-10-02; migration history, all three RPC bodies read directly from hosted and confirmed byte-identical to the reviewed local migration, SECURITY DEFINER/search_path hardening, grants, RLS, every Phase-6A constraint/index/trigger, and all three non-admin security probes all independently verified against hosted with zero rows inserted and zero existing rows mutated; see `current-state.md` for the full postflight record):
- `20261002100000_phase6b_contract_renewal_history.sql` — no schema changes (no new table, no new column, no `is_current`/`status`/`renewal_status`/`next_renewal_date`/`company_contract_periods`) — adds three narrow SECURITY DEFINER RPCs only, all `search_path = ''`, all Admin/superadmin-only, all granted to `authenticated`/`service_role`:
  - `renew_project_contract_period(p_project_id)` — records the successor of the Project's current leaf period (the one period nothing else has renewed from). Requires the Project's lifecycle to be Active or On Hold (rejects Completed/Canceled/Archived/Trash) and an existing recorded chain (rejects a Project with none — use `create_initial_project_contract_period` instead). Both `period_start`/`period_end` are always server-derived (`leaf.period_end + 1 day` -> December 31 of that year) — never accepted from the caller. Locks the Project row (`select ... for update`) for the duration of the call, serializing two concurrent renewal attempts on the same Project rather than letting them race; the Phase-6A unique indexes/trigger remain defense-in-depth regardless.
  - `delete_latest_project_contract_period(p_project_id, p_period_id)` — removes ONLY the current leaf period; rejects outright if the named period has a successor (a non-leaf can never be removed directly — later leaves must be removed first, one at a time, so the chain is never left disconnected). Removing a Project's sole root period is allowed. Lifecycle status is deliberately NOT checked here — correcting mistaken history is independent of whether the Project is currently renewal-eligible.
  - `correct_initial_project_contract_period_start(p_project_id, p_period_start)` — corrects the root period's `period_start` ONLY while it remains the Project's sole recorded period (no successor exists yet); `period_end` is always recomputed server-side as December 31 of the corrected year, `created_at`/`created_by` are never touched. Rejects outright once any renewal history exists — an established chain is never rewritten.
- Inserts/updates/deletes zero rows at migration-apply time (no data migration) — these are pure DDL (function definitions + grants). All three RPCs preserve every Phase-6A invariant (CHECK constraints, chain-continuity trigger, the three unique indexes, RLS, the `authenticated`-has-no-direct-write-grant boundary) untouched — none are weakened or bypassed.

Does not touch `project_contract_periods`' own schema (table, constraints, indexes, RLS, grants — all Phase-6A, unchanged), `companies.contract_start_date`/`renewal_date`, `projects.contract_months`/`contract_end_date`, `create_initial_project_contract_period` (Phase 6A, unchanged), any Project lifecycle-transition RPC (`set_project_status`/`trash_project`/`restore_project` — a status transition never reads or writes `project_contract_periods`, and this migration adds no trigger that would make it do so), System B, or the retired `renew_project` RPC (confirmed still absent, not restored — this migration's `renew_project_contract_period` is a distinct function name with a distinct, narrower contract). No automatic renewal, no `pg_cron` schedule, no hidden background behavior — every mutation requires a direct RPC call from an authenticated Admin session.
